The principle

Mandatory steps live in hooks. Thinking lives in agents.

Hooks are deterministic — they fire on their own, at fixed points, and can't be skipped, forgotten, or negotiated with. Putting "read the issue log" in a hook is why it stops getting skipped.

The problem → the structural fix

Six predictable failures, fixed in architecture — not discipline.

Even with disciplined practices, the same six mistakes recur whenever an AI agent is involved. The root cause isn't the model — it's that every "must happen" step was buried in a prompt the model could skip.

01

Missed the issue log

The session-start.sh hook injects open ISSUES.md every session, unconditionally.

02

Re-orienting every session

The same hook injects STATE.md, git state, and the research INDEX automatically.

03

Endless bug-flailing

A hard cap at 3 attempts: warn at 2, STOP at 3, and hand control back to you.

04

Context rot in debugging

The debugger works in an isolated context, writes detail to a file, returns a terse summary.

05

No orchestration

Nine scoped subagents; the orchestrator routes between them and never implements or debugs.

06

Handoff files bloat

The synthesizer plus the pre-compact.sh hook compress and dedup on every compaction.

Architecture

A three-part system, designed once.

Deterministic hooks that always run; scoped subagents the orchestrator routes between; and a declarative document layer it reads and hands off. The orchestrator routes only — it never writes code, runs tests, or debugs.

Workflow · one phase at a time

The spec is the contract. Tests are generated from it.

Phases that add a public callable surface run spec-first. The reviewable, authoritative artifact is the spec, not the test — so two agents can't independently fabricate the same wrong contract and go green on a broken core.

RESEARCH+ TDD applicability

Investigate, then classify

The researcher checks the shared KB and matching knowledge doc first, then returns a terse summary. The phase is classified TDD or not, and its E2E_KIND is bound.

SPEC FILLspec-author

Concrete cases into shared fixtures

The spec-author fills each case with real inputs, real expected outputs, and matcher tokens for volatile fields — grounded in research and the confirmed datasource baseline.

SPEC REVIEW· YOU · upstream gate

You confirm falsifiable claims

Before a line of logic: "empty order → 422 EMPTY_ORDER." SCAFFOLD can't begin until you approve the spec. Humans review the spec, never the test code.

SCAFFOLD → REDgenerated harness

Stubs, then generated tests that fail

Tests are GENERATED from the locked spec rows, loading the same fixtures — a test physically can't assert different values than the spec. Green-on-stubs is rejected.

GREEN+ boundary/E2E

Fill logic until the boundary passes

The implementer fills logic until the real boundary suite passes. spec-conformance.sh blocks GREEN while any TBD remains or any case-id is uncited.

CLOSEcoverage gates

Boundary run + evidence, then the gates

The boundary run for the phase's E2E_KIND must pass with evidence — screenshots for browser, transcripts otherwise — then the regression corpus, the ENDPOINTS gate, and the DATAFLOW transition gate.

New in v2.3 · Compression

Always-on, single-source, never model-invoked.

Output compression used to depend on an external skill invoked by a trigger phrase — a fragile vector for behavior meant to be always on. v2.3 makes it a kit-native reference with two named profiles. Mandatory behavior is wired by pointers, not invoked by pattern-match.

profile: user

Human-facing output. Terse, but keeps the Auto-Clarity exception — it expands for security warnings, irreversible-action confirmations, multi-step sequences, and clarification requests.

profile: internal

Agent-to-agent output. Harder compression, no clarity exception. Exact-output artifacts — fixtures, spec rows, generated tests — are exempted by structural gates in the emitter prompts.

New in v2.3 · Any project type

The core stopped assuming a web app on Azure.

The invariant core — loop, gates, doc system, commands — is now use-case agnostic. Web and Azure practice ship as preinstalled knowledge docs the researcher consults only when your declared project type calls for them.

Flags declared at /overview

One grill sets the project's shape — recorded in OVERVIEW.md, never inferred mid-phase.

The loop adapts

Phase 0 (infra) exists only when needed; the boundary run is selected by E2E_KIND; the final phase completes DEPLOY_KIND. Works for web apps, desktop apps, scripts, and libraries alike.

Commands you run

A straight line from idea to shipped.

A handful of commands drive the work. The bookkeeping — compressing context, logging issues and decisions — the system handles for you.

/overview

Design-research → a RESEARCH REVIEW you confirm → a double grill → OVERVIEW.md (with the project flags), DATAFLOW.md, and a vertical-slice PLAN.md.

/infra

Only when infra_needed: IaC → what-if diff → your review gate → apply → INFRA.md + .env.test → AUTH PROOF. Cloud specifics live in knowledge/azure.md.

/phase [n]

Run one phase end-to-end: SPEC fill → SPEC REVIEW → SCAFFOLD → RED → conformance → GREEN → boundary/E2E, with the coverage gates at CLOSE.

/quick /replan /unstuck

The escape hatches the loop is built around — a small direct change, a plan revision, or a deep re-research after the circuit breaker.

/synthesize /log-issueAUTO

Fired for you by hooks and the orchestrator — compaction, issue logging, and decision logging never depend on you remembering.

Everything in the kit

The complete capability set.

Each feature landed when it solved a specific, documented production failure — from the v1.0 foundation through v2.3. Nothing was bolted on for show.

Deterministic guardrails

  • Three lifecycle hooks — session-start, pre-compact, subagent-stop.
  • Nineteen hard rules injected into every single session.
  • SPEC REVIEW gate — you approve the spec before any logic is written.
  • Debug circuit breaker — a hard cap at three attempts.
  • Loud-fail verifiers for install, hook wiring & the AGENTS sentinel.

Spec-driven testing

  • Spec is the contract — tests are generated from locked case rows.
  • Shared fixtures — spec row and test load the same values.
  • Conformance + staleness gate scripts replace human test review.
  • Boundary run per E2E_KIND — browser, CLI, HTTP, or library API.
  • DATAFLOW coverage gate — every reachable transition has a filled case.

Compression & agents

  • Kit-native compression — two profiles, always on, never model-invoked.
  • Nine scoped subagents , each in its own context.
  • Orchestrator routes only — it never implements or debugs.
  • Isolated debugger — noise to a file, a terse summary back.
  • Author ≠ implementer — spec fixtures written before any code.

Adaptive core & distribution

  • Preinstalled knowledge docs — web & Azure practice, consulted on demand.
  • Adaptive flags — project_type, infra_needed, e2e_kind, deploy_kind.
  • Conditional Phase 0 — infra only when the use case needs it.
  • Shared KB across projects via /store-wisdom.
  • Upgrade-safe npx installer — manifest + sha256, non-destructive.
